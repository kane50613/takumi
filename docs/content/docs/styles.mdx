Takumi accepts styles in several ways, and the one to use depends on what you already have. The table maps each starting point to a section of this page.

| You have                                   | Use                                             |
| ------------------------------------------ | ----------------------------------------------- |
| Tailwind classes, compiled by your bundler | [`css`](#css) with the generated CSS            |
| Tailwind classes, no build step            | [the `tw` prop](#tailwind-without-a-build-step) |
| Plain CSS                                  | [`css`](#css) or a `<style>` tag                |
| Design tokens to theme with                | [a `:root` rule](#design-tokens)                |
| One-off styles on one node                 | [the `style` prop](#inline-styles)              |

You can mix them. Each section below says which declaration wins.

## Inline styles

The `style` prop sets `CSSProperties` on one node. It beats the tag default and every matching stylesheet rule of the same importance.

```tsx twoslash title="Style one element"
<div style={{ display: "flex", padding: 48, background: "#0f172a" }}>Hello</div>
```

## CSS

Pass stylesheet text, or a list of stylesheets, through `css`.

```tsx twoslash title="Apply a stylesheet"
import { render } from "takumi-js";

const image = await render(<div className="card">Hello</div>, {
  width: 1200,
  height: 630,
  // [!code highlight]
  css: `.card { display: flex; padding: 48px; background: #0f172a; color: white; }`,
});
```

A `<style>` tag in the JSX or HTML feeds the same stylesheet. Takumi pulls it out of the tree for you.

```tsx twoslash title="Embed a style tag"
<div className="card">
  {/* [!code highlight] */}
  <style>{`.card { display: flex; padding: 48px; }`}</style>
  Hello
</div>
```

The stylesheet supports:

- Selectors cover type, class, id, attribute, and combinators. They also cover structural pseudo-classes such as `:first-child` and `:nth-child()`, plus `:is()`, `:where()`, `:not()`, `:root`, `:lang()`, and `:dir()`, and the `::before` and `::after` pseudo-elements.
- At-rules cover `@media`, `@supports`, `@layer`, and `@keyframes`.
- Values cover custom properties with `var()`, `calc()`, and shorthands.

<Callout type="info">
  A render is one static frame. Interactive pseudo-classes such as `:hover` and `:focus` parse but
  never match.
</Callout>

### Media queries

`@media` reads the render's viewport and output:

| Feature                  | Reads                                                               |
| ------------------------ | ------------------------------------------------------------------- |
| `width`, `height`        | the viewport size                                                   |
| `aspect-ratio`           | the viewport ratio, as `16/9` or a number                           |
| `orientation`            | `portrait` or `landscape`                                           |
| `resolution`             | the device pixel ratio, in `dppx`, `x`, `dpi`, or `dpcm`            |
| `screen`, `print`, `all` | the media type: image renders are `screen`, PDF renders are `print` |

`width`, `height`, `aspect-ratio`, and `resolution` take `min-` and `max-` prefixes and the range syntax. Both `(min-width: 768px)` and `(400px < width <= 700px)` work. Combine queries with `and`, `or`, `not`, and parentheses.

<Callout type="warn">
  Any other feature, `prefers-color-scheme` included, matches nothing. The rest of the stylesheet
  still applies.
</Callout>

### Rule objects

A `css` entry can be an object instead of text. Use objects to keep application data out of CSS strings.

| Entry                        | Writes                                                       |
| ---------------------------- | ------------------------------------------------------------ |
| `{ selector, style, rules }` | a style rule, where `rules` nests child rules                |
| `{ keyframes, steps }`       | a [`@keyframes` rule](/docs/animation)                       |
| `{ media, rules }`           | a `@media` group holding entries of its own                  |
| `{ supports, rules }`        | a `@supports` group                                          |
| `{ layer, rules }`           | a `@layer` block, which declares order alone without `rules` |

```tsx twoslash title="Build CSS rule objects"
import { render } from "takumi-js";

const image = await render(<div className="card">Hello Takumi</div>, {
  width: 1200,
  height: 630,
  // [!code highlight:4]
  css: [{ layer: "theme" }, { selector: ".card", style: { background: "#ffffff", padding: 48 } }],
});
```

Takumi parses each prelude with its rule's grammar. A prelude that contains a block is rejected, so data cannot close the rule and open another.

## Tailwind with your bundler

Compile Tailwind with your bundler, then pass the generated CSS through `css`. Tailwind does the compiling, so every directive and class name works. The output is still limited to [what the stylesheet supports](#css). With Vite, import the stylesheet with `?inline`.

```tsx title="og.tsx"
import { ImageResponse } from "takumi-js/response";
// [!code ++]
import stylesheet from "~/styles/global.css?inline";

export function GET() {
  return new ImageResponse(
    <div className="bg-background text-foreground flex justify-center items-center w-full h-full text-4xl">
      Hello Tailwind!
    </div>,
    {
      width: 1200,
      height: 630,
      // [!code ++]
      css: stylesheet,
    },
  );
}
```

```tsx title="vite.config.ts"
import { defineConfig } from "vite";
import tailwindcss from "@tailwindcss/vite";

export default defineConfig({
  // [!code ++]
  plugins: [tailwindcss()],
});
```

## Tailwind without a build step

The `tw` prop runs a built-in Tailwind parser. It needs no build step. [Satori](https://github.com/vercel/satori#tailwind-css) uses the same prop name.

```tsx twoslash title="Use Tailwind utilities"
import { render } from "takumi-js";

const image = await render(
  // [!code highlight:3]
  <div tw="bg-blue-500 p-4 rounded-lg">
    <h1 tw="text-white text-2xl font-bold">Hello Tailwind!</h1>
  </div>,
  { width: 1200, height: 630 },
);
```

Arbitrary values work, but the parser does not cover every Tailwind feature. The [utility table](https://github.com/kane50613/takumi/blob/master/takumi-core/src/style/tw/utility.rs) lists every supported class. Check it when you migrate `next/og` templates.

`tw` is a plain string prop, so you can build it at runtime:

```tsx twoslash title="Build classes dynamically"
import clsx from "clsx";

const isError = true;

<div tw={clsx("p-4 rounded", isError ? "bg-red-100 text-red-700" : "bg-green-100 text-green-700")}>
  {isError ? "Something went wrong" : "Success!"}
</div>;
```

### Variants

Breakpoints such as `md:` apply when the viewport is at least that wide. Structural variants apply by the element's place in the tree, or by its contents for `empty:`, so one class list can style every row of a list:

```tsx twoslash title="Stripe and round a list"
const rows = ["Plan", "Seats", "Total"];

<div tw="flex flex-col">
  {rows.map((row) => (
    // [!code highlight]
    <div tw="p-3 bg-white odd:bg-slate-100 first:rounded-t-lg last:rounded-b-lg">{row}</div>
  ))}
</div>;
```

The structural variants are `first:`, `last:`, `only:`, `odd:`, `even:`, `first-of-type:`, `last-of-type:`, `only-of-type:`, `empty:`, `nth-3:` and its `nth-last-`, `nth-of-type-`, and `nth-last-of-type-` forms, `nth-[2n+1]:`, `not-first:` for any of them, and an arbitrary variant on the element itself such as `[&:nth-child(3)]:`. Variants combine, as in `md:first:mt-0`. When two structural variants set the same property, the one Tailwind lists later wins, so `odd:` beats `first:` whatever their class order. Interactive ones such as `hover:` never apply to a static frame.

`before:` and `after:` style the element's `::before` and `::after`, and `content-['…']` gives them their content. Write spaces in the string as underscores:

```tsx twoslash title="Add a badge after a title"
<h2 tw="text-2xl after:content-['NEW'] after:ml-2 after:px-2 after:rounded after:bg-amber-300 after:text-sm">
  Release notes
</h2>
```

As in Tailwind, the box exists without `content-*`, so `before:` utilities alone can draw a decoration such as a dot. Replaced elements such as `<img>` get no `::before` or `::after`.

### Preflight

The built-in parser applies no Tailwind Preflight by default. Elements keep their default margins, so an `<h1>` gets a `0.67em` top margin until you add `mt-0`. `box-sizing` still defaults to `border-box`.

<Callout type="warn">
  Without Preflight, a border style utility draws on every side. `border-dashed` sets `border-style`
  on all four sides, and an unset border width is `medium`. So `border-l-2 border-dashed` draws a
  2px left border and 3px borders on the other sides. Preflight's `border: 0 solid` reset removes
  them.
</Callout>

Add the import line a Tailwind stylesheet starts with to turn Preflight on. It removes default margins, list markers, and heading font sizes and weights.

```tsx twoslash title="Enable Preflight"
import { render } from "takumi-js";

const image = await render(<h1 tw="text-4xl">Hello Takumi</h1>, {
  width: 1200,
  height: 630,
  // [!code highlight]
  css: `@import "tailwindcss";`,
});
```

Tailwind's other entry points work the same way:

| Import                                                              | Preflight |
| ------------------------------------------------------------------- | --------- |
| `tailwindcss`, `tailwindcss/index.css`, `tailwindcss/preflight.css` | on        |
| `tailwindcss/theme.css`, `tailwindcss/utilities.css`                | off       |

This matches Tailwind's [setup without Preflight](https://tailwindcss.com/docs/preflight#disabling-preflight). Modifiers such as `layer(base)` and `source(none)` are ignored.

### Utilities in the cascade

Utilities sit in the last declared layer, as Tailwind orders them:

| Against a utility            | Winner           |
| ---------------------------- | ---------------- |
| An unlayered stylesheet rule | the rule         |
| A rule in a named `@layer`   | the utility      |
| The `style` prop             | the `style` prop |

Prefix a utility with `!` to flip the result. Important declarations reverse the layer order, so a `!` utility beats an unlayered rule and a normal `style` declaration.

Between two utilities that set the same property, Tailwind's order decides, not the class order. A utility for one side beats one for every side, so `pt-2 p-4` and `p-4 pt-2` both pad the top by `pt-2`. To let a later class override an earlier one, merge the class list first, as [`tailwind-merge`](https://github.com/dcastil/tailwind-merge) does.

### Tailwind at-rules

A Tailwind source stylesheet drops into `css` unchanged. Takumi reads these directives and skips the rest:

| At-rule                 | Reads as                                                                                                  | Rejected                |
| ----------------------- | --------------------------------------------------------------------------------------------------------- | ----------------------- |
| `@theme`                | its `:root` rule. Nested `@keyframes` register. Modifiers such as `reference` and `inline` change nothing | `prefix()`              |
| `@import "tailwindcss"` | [Preflight](#preflight) when the entry point brings it, at the top level only                             | any other import target |
| `@apply`                | the utilities' declarations, expanded in place, `!` suffix included                                       | variants such as `md:`  |

```css title="Define Tailwind utilities"
.card {
  @apply mt-4 bg-brand-500; /* [!code highlight] */
}
```

`@utility`, `@custom-variant`, `@source`, `@plugin`, and `@config` do not parse. Compile those with Tailwind and use [the bundler path](#tailwind-with-your-bundler).

## Design tokens

A utility reads a CSS custom property, the way Tailwind compiles it. `bg-red-500` resolves `var(--color-red-500)`, and `p-4` resolves `calc(var(--spacing) * 4)`. The built-in scale is the fallback, so you only declare tokens you want to change.

### Declaring tokens

Declare tokens in a stylesheet or in a rule object. Both feed every `var()`, whether it sits in a stylesheet, a `<style>` tag, or a utility.

A `:root` rule, or a [Tailwind `@theme` block](#tailwind-at-rules) pasted as-is:

```css title="Define design tokens"
:root {
  /* [!code highlight:2] */
  --color-brand-500: #5b21b6;
  --spacing-gutter: 2.5rem;
}
```

A rule object in `css`, so a token from application data needs no string concatenation. Takumi rejects a value that is not valid for its property, so the value cannot escape its rule.

```tsx twoslash title="Apply design tokens"
import { render } from "takumi-js";

const image = await render(<div tw="bg-brand-500 p-gutter">Hello</div>, {
  width: 1200,
  height: 630,
  // [!code highlight]
  css: {
    selector: ":root",
    style: { "--color-brand-500": "#5b21b6", "--spacing-gutter": "2.5rem" },
  },
});
```

### Which utilities read a token

The token's namespace decides which utilities read it:

| Namespace                                           | Utilities                                                                                                                                             |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--color-*`                                         | color utilities: `bg-*`, `text-*`, `border-*`, `outline-*`, `decoration-*`                                                                            |
| `--spacing`, `--spacing-*`                          | length utilities: `p-*`, `m-*`, `w-*`, `gap-*`, `inset-*`. `p-4` reads `calc(var(--spacing) * 4)`, `p-gutter` reads `var(--spacing-gutter)`           |
| `--container-*`                                     | `max-w-*`                                                                                                                                             |
| `--text-*`                                          | `--text-xl` sets `text-xl`, `--text-xl--line-height` sets its leading                                                                                 |
| `--font-*`                                          | font families, such as `font-sans`                                                                                                                    |
| `--font-weight-*`                                   | font weights, such as `font-bold`                                                                                                                     |
| `--tracking-*`                                      | `tracking-*`                                                                                                                                          |
| `--leading-*`                                       | `leading-*`                                                                                                                                           |
| `--radius-*`                                        | `rounded-*`, including corners and sides                                                                                                              |
| `--aspect-*`                                        | `aspect-*`                                                                                                                                            |
| `--blur-*`                                          | `blur-*` and `backdrop-blur-*` presets                                                                                                                |
| `--drop-shadow-*`                                   | `drop-shadow-*` presets                                                                                                                               |
| `--shadow-*`, `--inset-shadow-*`, `--text-shadow-*` | shadow preset shapes. A custom shape carries its own colors, so shadow color utilities only reach the built-in fallback                               |
| `--animate-*`                                       | `animate-*`. An unknown token such as `animate-wiggle` reads `var(--animate-wiggle)`. Pair it with its `@keyframes`                                   |
| `--breakpoint-*`                                    | the `sm:` to `2xl:` variants, and new ones such as `3xl:`. Variants apply before the cascade, so only an unconditional `:root` declaration moves them |

### Overriding tokens

Tokens in a stylesheet follow the cascade. A media query or a selector can override them:

```css title="Override tokens by viewport"
@media (width >= 1000px) {
  :root {
    --color-brand-500: #a78bfa;
  }
}
```

A rule object sits where its entry sits in `css`, so array order is cascade order:

| Competing declaration                  | Result                   |
| -------------------------------------- | ------------------------ |
| Equally specific `:root` rule earlier  | The later entry wins     |
| A more specific selector, `:root:root` | The selector wins        |
| Declaration on the element             | Element declaration wins |

## Where this differs from Tailwind

- Colors reach gradients and shadows. `from-brand-500` and `shadow-brand-500` read `--color-brand-500`, as `bg-brand-500` does.
- As in Tailwind, a gradient needs `bg-linear-*`, `bg-radial`, or `bg-conic`. Color stops alone paint nothing.
- `--color-red-500: initial` falls back to the built-in red. It does not remove `bg-red-500`.
- A bare `rounded` keeps its built-in value. `rounded-sm` and the others read the variable.
- `--spacing` needs a unit. With a bare number, `p-4` computes pixels here. A browser rejects that declaration.
- An aliased token stays live. `--color-brand: var(--background)` follows a `--background` override in a subtree. In a browser, you need `@theme inline` for that.
